## 2026-09-28 代码审查与稳定性修复


本轮先完整阅读实际源码、配置、测试、题目说明和任务书，再以代码为准核对 `CLAUDE.md`。
未运行摄像头（桌面 App 无摄像头权限），但完成了所有不依赖真实摄像头的自动验证。

**修复 1：摄像头线程退出冲突**
- 原因：`Camera` 把停止事件命名为 `self._stop`，覆盖了 `threading.Thread._stop()` 内部方法；
  `join()` 在线程结束时可能报 `Event object is not callable`。
- 修改：统一改名为 `self._stop_event`。
- 验证：用假摄像头启动线程，再调用 `stop()`；线程正常退出且资源已释放。

**修复 2：清零没有清干净动作周期**
- 原因：`Action.reset()` 原来只清计数和阶段，本轮峰值、谷值、规则极值等仍会带入下一轮。
- 修改：清零时同时重置 `sig_peak`、`depth_valley`、`rule_ext`、`last_values` 和
  `unit_smooth`，但不改变已经校准好的计数阈值。
- 验证：构造带残留状态的动作对象，清零后逐项断言全部恢复初始值。

**修复 3：低可信度帧会污染质量极值**
- 原因：旧代码虽然不让低可信度帧改变计数状态，但仍会把它写入峰值、谷值；
  自带信号的质量规则也没有单独检查自己的关键点可见性。幽灵骨架可能因此让错误动作误判为合格。
- 修改：只有计数关键点可信时才更新计数信号极值；质量规则还要单独确认其自身关键点可信，
  才能更新该规则的极值。
- 验证：分别构造低可信度膝关节帧和脚踝不可见帧，确认两类极值都不会被写入。

**验证结果**
- `.venv/bin/python test_pose_logic.py`：15 项全部通过。
- `.venv/bin/python -m py_compile ...`：全部 Python 文件通过语法编译。
- `git diff --check`：通过，无空白错误。
- 真实摄像头回归仍需用户从 macOS 系统「终端.app」执行；本轮没有虚构实测结果。


## 2026-09-28 动作规范与抗误计数改造


目标：标准动作不要卡得过严，但明显错误要及时提示；计数本身要稳，不能把走路、单边摆臂、
瞬时关键点跳变算成动作。当前无法使用摄像头，因此本轮只完成规范研究、代码改造和合成轨迹测试，
阈值仍是**待真实视频校准的工程初值**。

**动作规范依据**
- 深蹲参考 [ACE Bodyweight Squat](https://www.acefitness.org/resources/everyone/exercise-library/135/bodyweight-squat/)：
  髋膝共同屈曲、背部稳定、膝盖与脚趾方向一致、下蹲接近大腿平行，再伸髋伸膝站起。
- 俯卧撑参考 [ACE Push-up](https://www.acefitness.org/resources/everyone/exercise-library/41/push-up/)：
  躯干保持刚性，不能塌腰或撅臀；下放到胸/下巴接近地面，撑起时肘关节充分伸展。
- 开合跳参考 [ACE beginner HIIT guide](https://www.acefitness.org/resources/pros/expert-articles/5880/a-basic-high-intensity-interval-training-routine-for-beginning-exercisers/)：
  腿向外打开的同时双臂举过头，再并腿并把双臂放回体侧。
- MediaPipe 的 `visibility` 表示关键点是否在画面内且未被遮挡，依据
  [Google Landmark API](https://ai.google.dev/edge/api/mediapipe/python/mp/tasks/components/containers/Landmark)；
  计数和质量极值都必须先通过可见性过滤。

**本轮实现**
1. 状态机新增 `enter_hold`、`exit_hold`、`min_active_duration`：进入和退出阈值都要连续满足
   约 60ms，且 active 阶段至少持续 0.20–0.25s。迟滞区负责阈值边缘抖动，时间确认负责单帧跳变，
   `min_interval` 继续负责两次计数间隔，三层共同防抖、防重复。
2. 多条件状态机支持每个条件独立的 `direction=hi/lo`，为后续混合“角度变大/变小”条件留接口。
3. 开合跳从“只看左臂计数、腿只做质量提示”改为三条件同步门控：
   左臂肩角 ≥75°、右臂肩角 ≥75°、双脚横向距离 ≥0.95 倍肩宽才进入动作；
   双臂回落 ≤45°且脚距 ≤0.75 倍肩宽才完成一次。计数门槛宽松，质量标准更高
   （双臂峰值 ≥140°、脚距峰值 ≥1.25 倍肩宽），因此幅度不足仍能计数并收到语音纠正。
4. 深蹲质量线适度放宽：下蹲谷值由 95° 调到 105°，站直峰值由 162° 调到 160°；
   俯卧撑躯干直线、下压深度、伸臂标准分别放宽到 155°、110°、160°。
   这些修改减少边缘标准动作误报，但明显浅蹲、塌腰、下压不足仍会命中。
5. 每次真正进入 active 时清空此前未成形动作留下的极值，避免“先随便举一次手”替下一次
   幅度不足的动作通过质量检查。
6. MediaPipe 增加 `min_pose_presence_confidence=0.6`；多条件动作的 HUD 检测状态现在检查
   所有计数关键点，而不是只看第一条条件。
7. 语音路径保持非阻塞：明显的全程错误（如俯卧撑塌腰）可在动作中命中；深度、伸直、
   手脚幅度等周期性错误在完成一次动作时播报，错误优先于单纯报数，并有独立节流避免连续打断。

**新增反例测试（总数 18 项，全部通过）**
- 单帧角度跳变不进入 active；完整往返只计一次；停在还原位不重复计数。
- 走路式左右摆臂、单边举手、只抬双臂、只张双腿均不能计为开合跳。
- 未形成完整动作的旧峰值不会污染下一次动作质量判定。
- 标准开合跳计数且无报错；肩高但未过头、腿张幅不足会计数并产生对应提示。

**待真实素材验证**
- 75°/45°、0.95/0.75、140°、1.25 等值是依据动作几何与既有实测范围给出的初值，
  不是最终数据结论。拿到标准/错误视频后，需要画角度曲线，分别统计误计、漏计、误报和漏报，
  再微调阈值；在这之前不要把当前版本写成“新参数已实测准确”。


## 2026-09-29 动作设定校准（按权威依据重定阈值 + 膝超脚尖 + 中文叠加）


### 依据来源（不再拍脑袋）

| 结论 | 出处 |
|---|---|
| 平行蹲：大腿与地面平行，膝关节屈曲「稍大于 90 度」→ **MediaPipe 膝角 ≈ 90°** | [丁香医生《无深蹲，不翘臀，你蹲对了吗？》](https://dxy.com/article/3265)（审稿委员会评议通过） |
| 浅蹲：膝关节屈曲 15~30° → 膝角 **150~165°** | 同上 |
| 深蹲要求：腰背直线、髋低于膝，且「**膝关节不要超过双脚尖**」 | 同上 |
| 俯卧撑下压到位：「屈肘至上臂与小臂成 **90°**」 | 教学规范；ACE 亦强调下降到胸/下巴接近地面 |
| 俯卧撑身体刚性：头肩髋膝踝保持整体对齐 | [ACE Push-up](https://www.acefitness.org/resources/everyone/exercise-library/41/push-up/) |

注意：临床「膝关节屈曲角」（完全伸直=0°）与 MediaPipe 的 `∠髋膝踝`（完全伸直=180°）
互为补角，**膝角 = 180° − 屈曲角**。所以「平行蹲屈曲≈90°」对应「膝角≈90°」。

### 校准原则：计数宽松、质量严格（这次真的分开了）

| 动作 | 参数 | 原值 | 现值 | 为什么 |
|---|---|---|---|---|
| 深蹲 | 蹲够深（谷值） | 115° | **105°** | 平行蹲≈90°、浅蹲 150~165°；105° 比平行蹲松、比浅蹲严 |
| 深蹲 | 站直（峰值） | 160° | 160° | 站立≈175°，160° 相当于「接近伸直」 |
| 深蹲 | **膝不超脚尖** | 用 `dx` 绝对值 | **改用 `dxs` 带符号** | 绝对值分不清「膝在前」还是「膝在后」，意义完全相反 |
| 俯卧撑 | 下压够深 | 115° | **105°** | 「上臂与小臂成 90°」为到位；105° 留一点余量 |
| 俯卧撑 | 撑起伸直 | 155° | 155° | 完全伸直≈175~180° |
| 俯卧撑 | 身体直线 | 155° | **160°** | ACE 要求躯干刚性；160° 才抓得住明显塌腰 |
| 开合跳 | 手举过头（肩角峰值） | 135° | **140°** | 举过头顶≈160~175°；140° 是「接近过头」 |

### 新增信号 `dxs`（带符号水平差）

```json
{"name": "knee_over_toe", "signal": "dxs", "points": [31, 25],
 "unit_points": [11, 12], "check": "valley_min", "min": -0.10,
 "priority": 90, "tip": "膝盖超过脚尖了，试着把髋部向后坐"}
```

- `dxs = pts[0].x − pts[1].x`，**不取绝对值**；配置里写 `[脚尖, 膝]`
- 人面朝画面右侧时：正常深蹲结果为正（膝在脚尖后），膝越过脚尖变负
- 阈值 `-0.10`（允许膝略微超过脚尖 0.10 倍肩宽，只抓明显前移）

⚠ **真实几何提醒**：脚尖应在脚踝**前方约 0.4 倍肩宽**（脚长 15~18cm ÷ 肩宽 40cm）。
早期测试把脚尖放在脚踝正下方，导致蹲下时被误判成「膝超脚尖」—— 测试合成数据必须
符合真实人体比例，否则测出来的阈值是错的。

### 画面中文叠加（解决 cv2.putText 不支持中文）

- `cv2.putText` 只认 ASCII，中文会画成「????」，所以之前 HUD 全是英文、中文只靠语音。
- 现改为 **PIL 渲染**：`render_cn()` 把一行中文渲染成 numpy 小图，**带缓存**；
  `blit_cn()` 每帧只做 numpy 贴图（纯赋值，很快）。
- 为什么不每帧都调 PIL：PIL 转整帧再转回的开销会掉帧；而提示文案组合有限（几十种），
  渲染一次存下来即可。缓存上限 64 条，超了清空。
- 字体自动从系统候选里挑（`STHeiti Medium.ttc` → `Hiragino Sans GB.ttc` → `Songti.ttc`），
  **Pillow 缺失或字体加载失败会自动降级为纯英文 HUD**，不影响主流程。
- 显示位置：画面**底部**两行 —— 上行「动作名 · 阶段 · 次数」，下行「⚠ 变形提示」（红色）。
  英文 HUD 保持原位不动。

### 测试

- `test_pose_logic.py` 从 24 项增至 **26 项**，全部通过。
- 新增：**测试 25**（膝超脚尖走完整状态机：正常深蹲不报 / 膝越过脚尖要报）、

- 同步修正了测试里「脚尖长在脚踝正下方」的错误几何。

### 关键设计

1. **时间由调用方注入**（`now` 参数）—— 测试里可以精确模拟时间流逝，不用 `sleep`，
   所以组间休息、跨周统计这些都能被稳定测试。
2. **`on_rep` 收「当前总计数」而不是「+1」** —— 和外部计数器解耦：外部按 `r` 清零时，
   这里也能跟着对齐，不会错位。代价是要记 `_last_seen` 做差分。
3. **一次喂进多次要能连跳多组** —— 离线视频跑得比 UI 刷新快，可能一次涨好多次；
   `while` 循环处理跨组，测试 2 专门验证「一次喂 12 次跨过 2 个满组」。
4. **休息期间的计数不算数** —— 否则用户休息时随手动一下就把下一组次数吃掉了。
5. **原子写 JSON**（先写 `.tmp` 再 `os.replace`）—— 避免中途崩溃留下半个文件。
6. **数据目录可用环境变量覆盖**（`FITNESS_DATA_DIR`）—— 测试隔离用，不污染真实数据。
7. **`data/` 已加入 `.gitignore`** —— 个人训练记录不进版本库。

## 2026-09-29 UI 动态扫描 configs/（补上「配置驱动」最后一环）


### 之前的问题（答辩会被问住）

「新增动作只写 JSON、不改代码」这个核心卖点，**在 UI 层是假的**：

```python
# fitness_ui.py 旧代码
ACTION_IDS = {"俯卧撑": "pushup", "深蹲": "squat", "开合跳": "jumping_jack"}
REFERENCE_VIDEOS = {"俯卧撑": ROOT / "...pushup_standard.ogv", ...}
```

命令行 `realtime_pose.py --action X` 确实是从 `configs/X.json` 动态加载的，
但**界面里的动作按钮是写死的** —— 往 `configs/` 里丢一份新 JSON，界面不会有任何变化。
一旦被问「那你加个动作给我看看」，就会露馅。

### 现在改成了什么

```python
def discover_actions(config_dir=None):
    """扫描 configs/*.json，返回 [(显示名, 动作id), ...]"""
```

- 界面动作按钮**由扫描结果动态生成**，新增动作 = 丢一份 JSON，界面自动多一个按钮。
- 参考视频也改成**按 id 自动匹配** `captures/reference/<id>_standard.*`，不再写死文件名。
- `build_command()` 改为接收**动作 id**（之前接收显示名，中间还要查一次字典）。
- 新增 `action_id()` 方法负责「显示名 → id」的换算，UI 内部只认 id。

### 容错设计

`discover_actions()` 遇到**无法解析的 JSON 会跳过它自己并打印提示**，
而不是让整个界面起不来 —— 写错一份配置不该导致测试台完全不可用。
测试里专门丢了半份坏 JSON 验证这一点。

### 验证

测试 24 重写为 `test_ui_discovers_actions_from_configs`，直接验证这个闭环：

```
扫描 configs/ -> [('开合跳','jumping_jack'), ('俯卧撑','pushup'), ('深蹲','squat')]
丢进一份新 JSON -> UI 发现 [('侧平举','lateral_raise')]      ← 无需改代码
再丢一份坏 JSON -> 仍然只有 [('侧平举','lateral_raise')]      ← 坏配置被安全跳过
深蹲参考视频自动匹配：squat_standard.webm
```

- `test_pose_logic.py` 26 项全绿；UI 动态扫描版本已实际启动确认（进程存活、无报错）。
- ⚠ 界面按钮的视觉呈现仍需在有图形上下文的环境里肉眼确认，本环境无屏幕录制权限。

### 现在「配置驱动」是完整闭环了

| 环节 | 是否配置驱动 |

| 判定逻辑（信号/阈值/约束/时机） | ✅ `pose_logic.py` 解释器 |

### 二、「按键不灵敏」的两个真实原因

用户反馈按钮点不动、要点两次。**排查出两个独立原因**，都不是「macOS 的问题」那么简单：

**原因 1：日志消费把主线程占满了（真正的主因）**

```python
# 旧代码
def _poll_messages(self):
    try:
        while True:                      # ← 无限循环消费队列
            kind, value = self.messages.get_nowait()
            self._append_log(value)      # 每次 insert 都触发 Text 重绘
```

识别进程每秒会吐不少行日志（每帧的判定明细），这个 `while True` 会一直消费到队列空为止，
**主线程被日志刷满 → tkinter 没机会处理鼠标事件 → 按钮看起来「点不动」**。

改法：每轮**最多处理 60 条**，剩下的留给下一轮（`after(80, ...)`），保证事件循环有喘息。

**原因 2：macOS 非活动窗口的第一次点击只「激活窗口」**

识别子进程启动时会把前台焦点抢走，而 macOS 上**非活动窗口的第一次点击不会传递给按钮**
（click-through 行为）。所以用户要点两次。

改法（两条一起上）：
1. **鼠标在控制台里移动时把键盘焦点抢回来**（绑 `<Motion>` + `<Enter>`，节流到每秒一次）——
   鼠标在 UI 上就说明用户要用 UI，这时抢焦点不会干扰识别窗口；鼠标在识别窗口时不会触发。
2. **启动子进程后延迟抢两次焦点**（1.2s / 2.8s），抵消「子进程启动抢焦点」那一下。

**附带修掉的隐患**：日志文本原来会无限增长，Text 控件重绘会越来越慢最终整个界面发卡。
现在超过 1500 行就砍掉最前面一段。

## 2026-09-29 合成动作轨迹生成器（终于绕开「没有真人视频」这个死结）


### 核心思路

真人标准/错误动作视频拿不到（用户无法自录，网上素材适用性差）—— 但**阈值行为本身是可以验证的**：

> 用程序生成**符合人体比例**的关键点轨迹，覆盖「标准动作」与「各类典型错误」，
> 再检查程序是否按预期计数、是否按预期报出对应错误。

这本质上是把「参数敏感性分析」做成**可重复、可回归、不依赖任何视频**的自动化测试，
而且变量的控制比真人拍摄严格得多（不受机位、光照、体型、遮挡影响）。

新增 `motion_synth.py`：

```bash
.venv/bin/python motion_synth.py --all                    # 13 条内置用例（标准+错误）全跑
.venv/bin/python motion_synth.py --action squat --depth 110
.venv/bin/python motion_synth.py --sweep squat --param depth --lo 85 --hi 175 --step 10
```

### ⭐ 参数扫描给出「阈值的安全边界」（答辩材料）

以深蹲下蹲深度为例：

| 下蹲深度 | 程序行为 |
|---|---|
| 85° | 计数，但报「膝超脚尖」（蹲太深，膝必然前移） |
| **95°** | ✅ 计数 + 全部合格 |
| 105° | 计数 + 报「蹲得不够深」 |
| 145° 以上 | **不计数**（连计数门槛 140° 都没到） |

开合跳腿距扫描：`<0.95` 不计数 → `1.0` 计数并报「腿没张开」→ `≥1.2` 合格。

**这条曲线就是「阈值定得合不合理」的直接证据**，比空口说「我调过参」有力得多。

### 合成器本身也需要被验证（关键教训）

第一版跑出来 **13 条用例有 9 条不符合预期** —— 但排查后发现**全是合成器的几何 bug**，
不是阈值问题。这恰恰说明：**用错误的合成数据去判断阈值，只会得出错误的结论**。
四类 bug：

| 现象 | 根因 |
|---|---|
| 标准深蹲被判「膝超脚尖」 | 我用了**对称折叠**（大腿后倾 = 小腿前倾），而真实深蹲是「髋部后坐 + 小腿适度前倾」。对称解会让膝跑到脚尖前面 |
| 注入「膝前移」反而不报 | 参数方向写反了（应该是小腿前倾**增大**） |
| 俯卧撑「塌腰」检查不出来 | 我让整条身体一起倾斜 → 肩-髋-踝**仍然共线**，`collinear` 永远命中不了。塌腰的定义是「肩踝基本不动、只有髋下沉」 |
| 开合跳一个都不计数 | ① 手臂公式 `cos` 符号写反（手举到身下而不是头顶）；② `foot_ratio` 被当成「额外张开量」而不是「脚距/肩宽」，传 0.10 实际得到 0.95，超过退出线 0.75，永远回不到并拢态 |

### ⭐ 顺带发现一个真实的算法缺陷（已修）

「上身前倾」原本用 `segment_angle_diff`（躯干与**小腿**的方向差）判断 —— 但**深蹲时躯干和小腿会同步前倾**，
方向差很小，**根本抓不到上身前倾**。

改法：新增 **`tilt` 信号**（两点连线相对**竖直方向**的夹角），并给 `squat.json` 加约束：

```json
{"name": "torso_lean_excessive", "signal": "tilt", "points": [23, 11],
 "check": "peak_max", "max": 45, "when": "on_rep", "priority": 80,
 "tip": "上身前倾太多，挺胸并保持核心稳定"}
```

原来的 `torso_shin_mismatch` 降级为「极端失配」兜底（阈值放宽到 60°）。
`validate_config.py` 的 `SIGNAL_ARITY` 同步加入 `tilt: 2`。

### 验证

- `motion_synth.py --all`：**13 条用例全部符合预期**（标准动作不报错、错误动作都抓住）。
- `test_pose_logic.py` 增至 **28 项**（新增合成轨迹回归），全绿。
- `test_training_manager.py` 7 项全绿。
- 参数扫描功能实测可用（深蹲深度、开合跳腿距的翻转点都符合阈值设定）。

### 对报告口径的影响（重要）

「阈值现状」章节原先写的是「无法用真人视频校准」。现在可以补上一句更有力的话：

> 在无法获取真人标注视频的条件下，采用**合成动作轨迹**做参数敏感性分析：
> 按人体测量比例生成标准动作与 13 类典型错误动作的关键点序列，
> 扫描关键参数定位判定翻转点，验证阈值落点符合动作规范。
> 合成数据不替代真人场景的检出率验证，但**能严格验证判定逻辑与阈值行为**，
> 且完全可重复、可回归。

## 2026-09-28 模块 3（动作质量判定）完整强化


本轮目标是让质量判定做到“标准动作不过度挑剔，明显错误快速发现”，而不是简单堆阈值。
实现范围覆盖当前可运行的三个动作：俯卧撑、深蹲、开合跳。

### 已完成的判定能力

1. **双侧判定**：俯卧撑同时检查左右身体直线、左右下压深度、左右撑起伸直；
   深蹲同时检查左右深度和左右站直。不会再只看靠近镜头的一条胳膊/腿。
2. **左右同步性**：新增 `angle_pair_diff` 几何信号；俯卧撑可发现两臂不同步，
   开合跳可发现两臂明显不同步。阈值为宽松的 35°，小幅自然差异不会报警。
3. **深蹲明显变形**：新增膝盖相对脚尖的归一化水平位移兜底，以及
   `segment_angle_diff`（躯干与小腿方向差）。两者只在完成一次动作时用整个周期极值结算。
4. **错误确认防抖**：实时姿态错误默认连续 3 帧不合格才提示；单帧关键点漂移不报警。
   `on_rep` 类型已经使用整个动作周期极值，计数完成时立即反馈，不再额外拖延。
5. **严重问题优先**：每条规则支持 `priority`；同时出现多个问题时先显示、播报高优先级项。
6. **异常几何丢弃**：关节两点重合时角度没有意义，现在返回不可判定，不再伪造成 90°错误。
7. **宽松阈值**：俯卧撑/深蹲到位线较计数线严格、但较教科书理想值留有余量；
   开合跳举臂标准降为 135°、腿距标准为 1.20 倍肩宽，避免对正常动作过严。

### 专业依据与边界

- ACE 俯卧撑强调头、肩、髋、膝、踝保持整体对齐，并控制下降到胸或下巴接近地面。
- NASM 深蹲资料强调膝盖沿第二/第三脚趾方向、避免膝内扣，保持中立脊柱和稳定脚掌；
  深度应服从个人活动度和控制能力，并非所有人必须达到同一个绝对深度。
- “膝盖绝不能超过脚尖”不是适用于所有体型和深度的绝对标准。因此程序仅对**非常明显**的
  前移给宽松提示，不把轻微过脚尖直接判错。
- 单侧摄像头不能同时高质量观察所有问题：侧视适合深度、躯干和膝前移；膝内扣应从前方观察。
  当前不把二维侧视无法可靠推断的旋转、关节受力或伤病风险包装成精确诊断。
- 这是运动姿态反馈，不是医疗诊断。

## 2026-09-28 三动作测试 UI


新增 `fitness_ui.py`，作为面向调试和验收的桌面控制台。启动方式：

```bash
.venv/bin/python fitness_ui.py
```

功能：

1. 动作下拉框仅保留最终确定的俯卧撑、深蹲、开合跳。
2. 输入可选内置参考视频、本地视频或摄像头编号；内置素材会随动作自动切换。
3. 支持语音开关、开始、停止和“清零并重启”。识别画面继续使用经过验证的 OpenCV HUD
   独立窗口；控制台显示子进程日志。MediaPipe 放在子进程中，底层 Metal 异常不会拖垮 UI。
4. 每次自然结束会在 `captures/reports/` 生成 JSON 摘要，包含动作、来源、计数、处理帧数、
   关键点检出帧数、检出率、各错误事件次数和结束原因；UI 同步显示核心结果。
5. `realtime_pose.py --src` 已修复：文件按原帧率逐帧消费，每帧只处理一次，EOF 自动退出；
   新增 `--no-voice` 和 `--report 路径` 参数。
6. 自动测试增至 **24 项**；新增“视频逐帧且 EOF 自动结束”和“UI 为三个动作生成正确参数”。

验证边界：UI 窗口进程已成功启动并保持运行；当前自动化环境没有 macOS 屏幕录制权限，
无法自动截图做视觉核对。MediaPipe 真视频运行仍需要从有图形上下文权限的系统终端启动 UI。

### UI 交互修正（用户实际试用反馈）

第一版用只读下拉框选择动作和输入，在用户环境中无法可靠切换；且默认选择参考视频，偏离了
“打开后直接自己做动作”的核心流程。现已改为：

1. 动作改成三个始终可见的大按钮：俯卧撑 / 深蹲 / 开合跳，不再依赖下拉菜单。
2. 输入改成始终可见的单选按钮；默认选择**摄像头**，参考视频和本地视频只是可选调试入口。
3. 摄像头默认选择已实测的**手机摄像头设备 1**；可一键切换电脑摄像头设备 0，
   也保留其他设备编号输入。
4. 第一版“清零并重启”直接终止子进程，不是真正清零。现在 UI 与识别进程通过原子 JSON
   控制文件通信：`reset` 会立刻清除次数、动作阶段、帧统计和错误统计；`stop` 会正常结束并
   写报告；“重新启动”会在正常停止后自动开始新测试。若进程 2.5 秒没有响应才强制终止。
5. 控制不依赖 OpenCV 窗口键盘焦点，因此用户在 UI 中点击清零/停止/重启均可生效。
