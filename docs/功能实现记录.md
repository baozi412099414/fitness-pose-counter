## 2026-09-29 动作评分系统（0~100 分）

原来的判定只有「合格 / 不合格」两种结果，**「刚好压线」和「做得很好」区分不出来**。
现在每条约束都能出分，加权汇总成总分，于是训练历史里多了一条能画成曲线的指标。

### 评分规则

| 概念 | 含义 | 分值 |
|---|---|---|
| 及格线（配置里的 `min` / `max` / `min_angle`） | 现有阈值，不变 | **60 分** |
| 满分线（新增可选字段 `ideal`） | 做到这个程度算完美 | **100 分** |
| 不及格 | 偏离阈值越多扣得越狠 | 60 → 0 分线性衰减（**偏离 50% 归零**）|

`ideal` 没配时自动外推 15%，并且**角度类上限 179°** —— 否则「站起伸直」（阈值 160°）
的满分线会算成 184°，永远拿不到满分。

### ⭐ 两个关键设计（都是被数据打回来才改对的）

**一、评分必须在「动作完成那一刻」结算**

`on_rep` 类约束只在计数那一帧才 `checked=True`。最初拿别的帧去算分，结果
**浅蹲也能拿 100 分**（它的「蹲得不够深」根本没被算进去）。
现在 `Action.last_score` 在 `just_counted` 时结算，此时周期极值已完整。

**二、总分不能单纯用加权平均**

浅蹲的人幅度分只有 30，但其他几条姿态都没毛病（满分），平均下来还有 80 分，
完全体现不出「蹲不到位」这个核心问题。

改成：**总分 = 0.5 × 加权平均 + 0.5 × 最低分**（木桶效应）。
任何一条明显不合格都会直接把总分拉下来，同时保留整体水平的区分度。

验证结果（合成轨迹，同一动作越标准分越高）：

```
深度 135→90° 的分数序列：[47.9, 59.4, 71.4, 78.3, 83.4]   ← 单调上升 ✅
上身前倾 55°          58.2 分（待改进）
膝明显超脚尖           34.0 分（待改进）
标准开合跳            100.0 分（优秀）
```

### ⭐⭐ 顺带挖出一个真实的算法缺陷：侧视机位误用肩宽归一化

`squat.json` 的 `knee_over_toe` 原来用**肩宽**当归一化基准，结果**标准深蹲都被判成
「严重膝超脚尖」**（实测 -0.21，阈值 -0.10）。

根因：**侧视机位下肩宽的水平投影只有真实肩宽的约 0.24 倍**（左右肩前后重叠），
拿它当尺子会把膝盖前移量**放大约 4 倍**。

改法：归一化基准换成**小腿长（膝→踝）** —— 侧视下投影稳定，且与「膝-踝-脚尖」
本就在同一平面内。换完之后膝前移量回到 -0.072，判定恢复正常。

> 这与「设计经验」第 7 条（距离类信号不如角度类稳）是同一个坑的两个面：
> **不光信号本身要选对，归一化的「尺子」也必须选侧视下投影稳定的长度。**

### 接入位置

| 位置 | 表现 |
|---|---|
| HUD（中文叠加） | `深蹲 · 动作中 · 12 次 · 85 分（良好）` |
| JSON 报告 | 新增 `score` 与 `grade` 字段 |
| 训练历史 | 每条记录带 `score`；**无分数的旧记录被跳过，不会当成 0 分** |
| 趋势图 | 新增第三个子图「每日动作评分」+ 及格线 60 / 良好线 85；没练的日子曲线自动断开 |
| UI「最近一次结果」 | 新增「动作评分」列 |
| 配置校验器 | 检查 `ideal` 方向是否与 `min`/`max` 一致（写反了会直接报错）|

### 验证

- `test_pose_logic.py` 增至 **29 项**（新增评分测试：单调性、低分惩罚、等级映射、范围约束）。
- `test_training_manager.py` 增至 **8 项**（新增评分历史统计测试）。
- 三个正式配置各配了 `ideal`，校验仍为零错误。
- 趋势图已实际生成并肉眼核对（评分曲线、断点、参考线都正常）。


## 2026-09-29 UI 内嵌趋势图（下方改标签页布局）

原来「查看趋势图」是拉起 `plot_trend.py` 子进程弹一个独立窗口 —— 看图要来回切窗口，
而且看不到「当前用户 / 当前动作」对应的图。现在直接内嵌在界面里。

### 布局变化

界面下半部分改成 `ttk.Notebook` 三个标签页：

```
[ 训练趋势图 ] [ 历史与统计 ] [ 运行日志 ]
```

- **趋势图页**：内嵌 matplotlib 画布（`Figure` + `FigureCanvasTkAgg`），
  标题栏显示「当前用户 / 当前动作 / 最常犯的错」，并提示「切换用户或动作会自动重画」。
- 没有训练记录时显示提示文字，而不是画一张空图。
- 本机缺 matplotlib Tk 后端时显示提示并降级（仍可用「查看趋势图」按钮另存图片）。

**重画时机**：启动、切换用户、切换动作、跑完一次测试 —— 都会自动重画。

### 关键设计：绘图逻辑抽成共用函数

```python
# plot_trend.py
def build_axes(fig, axes, hist, goals, action=None, weeks=8, days=14):
    """把三张子图都画到给定的 axes 上（命令行脚本与 UI 内嵌共用）"""
```

`plot()`（命令行，pyplot 建 figure）和 `fitness_ui._draw_trend()`（界面，自建 Figure）
都调它。**抽出来的理由很实际**：两边各画各的话，改了一处忘了另一处就会不一致
（比如加了评分曲线却只在脚本里生效）。

**一个容易踩的坑**：UI 里**只 import `Figure` 和 TkAgg 画布，不调用
`matplotlib.use()`** —— 因为 `plot_trend.py` 在无图形环境时会切到 `Agg` 后端，
两边争抢全局后端会互相干扰。中文字体设置也由 `plot_trend` 统一负责（UI 从它 import）。

### 验证

- `test_training_manager.py` 测试 6 扩展为**同时覆盖两条路径**：
  命令行脚本（pyplot）与 UI 内嵌（Figure）都能出图，且共用 `build_axes`。
- UI 已实际启动确认（标签页 + 内嵌画布，进程存活无报错）。
- 三个动作的回归测试、配置校验全部仍然通过。


## 2026-09-29 UI 可用性修复（滚动 + 窗口层级）

### 一、界面加垂直滚动

界面内容太长（测试设置 + 训练管理 + 按钮 + 结果 + 三个标签页），矮屏上最下面的
趋势图会被挤出可视区。改法：

- 主内容区放进 `Canvas` + `Scrollbar`，内容变高时自动出现滚动条。
- 窗口尺寸**按屏幕自适应**：`height = min(1060, max(620, 屏幕高×86%))`，并居中。
- **趋势图画布固定 330px 高** —— 可滚动容器里不能用 `expand=True`，否则控件高度
  会塌成一条线（这也是「看不到图」的原因之一）。
- 鼠标滚轮只取**方向**（`-1 if delta > 0 else 1`），规避各平台 delta 量纲差异。

### 二、⭐ 窗口层级：一个自己挖的坑

用户反馈：**点击按钮的提示出现在 UI 后面，连摄像头画面也上不来。**

排查出**三个叠加原因**，全是之前为了修「按键不灵敏」时引入的：

| 原因 | 后果 |
|---|---|
| `self.root.attributes("-topmost", True)` **持久置顶** | macOS 上 topmost 窗口永远压在所有普通窗口之上 → 摄像头画面、消息框、文件对话框全被挡住 |
| `_grab_focus()` 里调了 `self.root.lift()` | 每次抢焦点都把控制台抬到识别画面之上 |
| 14 处 `messagebox` **都没指定 `parent`** | macOS 上无 parent 的消息框会跑到主窗口后面，用户以为「点了没反应」 |

**改法**：

1. **不持久置顶**，改成 `_flash_topmost()`：置顶 0.9 秒后自动取消（提醒用户但不挡人）。
2. **抢焦点只做 `focus_force()`，绝不 `lift()`** —— 键盘焦点和窗口层级是两回事，
   之前把两者混在一起了。
3. **所有弹窗走统一的 `self._msg(kind, title, message)`**，内部 `setdefault("parent", self.root)`。
   包一层的好处是以后新增弹窗不会再漏掉 parent。
4. **鼠标抢焦点条件收紧**：节流从 1 秒放宽到 3 秒，且**只在本窗口确实没有键盘焦点时**
   才抢（`focus_displayof() is None`）—— 否则会不停和识别画面抢焦点，
   导致 `q` / `r` 按键在画面窗口里失灵。

**教训**：修「点击不灵敏」时为了抢焦点用了 `topmost` + `lift`，把「窗口层级」和
「键盘焦点」当成了同一件事 —— 结果解决了点击问题，却让别的窗口全都上不来。
**这两件事必须分开处理。**

### 三、滚动卡顿优化

用户反馈「滑动界面有点卡卡的」。排查出**四个叠加原因**：

| # | 问题 | 为什么卡 |
|---|---|---|
| 1 | **`<Motion>` 绑定抢焦点** | 鼠标每移动一点就触发一次 Python 回调，快速划过时可达**数百 Hz**；tkinter 的 Python 回调开销大 —— **这是主因** |
| 2 | 滚轮**每次只滚 1 单位** | 触控板一秒能发几十个事件，每次都重绘 |
| 3 | `<Configure>` 直接调 `bbox("all")` | `bbox` 相对慢，且布局期间会连续触发很多次 |
| 4 | 没设 `yscrollincrement` | 每次滚动都要重新计算滚动单位量 |

**改法**：

1. **只绑 `<Enter>`，不绑 `<Motion>`** —— `<Enter>` 只在鼠标进入窗口边界时触发一次，
   已经足够解决「第一次点击只激活窗口」的问题，没必要每次移动都跑一遍。
2. **滚轮节流 16ms + 步长放大到 3 个单位** —— 事件数直接降到 1/3，且上限约 60fps。
3. **`<Configure>` 用 `after_idle` 合并** —— 用一个 `_scrollregion_pending` 标志位去重，
   布局期间无论触发多少次，最终只算一遍 `bbox`。
4. **`canvas.configure(yscrollincrement=18)`** —— 固定每次滚动的像素量。

**教训**：抢焦点别用 `<Motion>`。它看起来只是个「鼠标动了一下」的事件，
但 tkinter 每个事件都要走一遍 Python 解释器 —— 高频事件必须换成低频替代
（`<Enter>`）或者内部节流。**「功能能用」和「用起来不难受」是两件事。**

### 四、趋势图窗口自动对齐（一个「空图让人以为坏了」的坑）

启动 UI 时发现「近 7 天平均分 = None」，一查才发现**系统日期是 2026-10-12**，
而演示数据是 2026-09-08 ~ 09-27 —— 「最近 14 天」自然是空的。

数据没问题，但这暴露一个**真实的可用性缺陷**：

> 用户很久没训练时，打开界面看到的是**一张空图** —— 会很自然地以为「功能坏了」，
> 而历史数据其实一条都没丢。

**改法**：新增 `plot_trend.resolve_window(hist, action, days)`：

- 最近 N 天有数据 → 正常显示；
- 最近 N 天**完全没记录** → 把窗口前移到「最后一次训练」那天；
- 标题如实写明实际区间：`（截至 2026-09-27（最近 14 天无记录，已向前对齐），共 361 次…）`。

⚠ **关键是不假装**：挪窗口只是别让空图误导人，标题必须说清楚这不是「最近 N 天」的数据，
否则就成了另一种误导。**「不要显示空图」和「不要伪造时间范围」两件事都要满足。**

### 验证

- 12 个 Python 文件语法正常；UI 启动确认无报错。
- 37 项测试全绿；测试 6 补充验证「无近期数据时窗口前移、有近期数据时不动」。
- 趋势图已实际生成并肉眼核对（对齐后的三条曲线都是满的，标题写明实际区间）。


## 2026-09-29 真机测试问题排查（用户实测反馈）

用户实测反馈四类现象：**全是错误 / 卡住 / 不计数 / 两个界面来回乱跳**。
逐个定位，找到**三个真实原因**（其中两个是这次新引入或一直没暴露的）。

### 一、两个界面来回乱跳（抢焦点打架）

```
UI 侧：     启动子进程后 1.2s / 2.8s 抢焦点 + 鼠标进入时也抢
识别侧：    realtime_pose 第一次出画面时 bring_window_to_front()
→ 两边互相抢，窗口来回跳，用户根本看不清画面
```

**改法 —— 明确分工**：

- **识别运行期间，UI 完全不抢焦点**（`_maybe_grab_focus` 里先判断子进程是否在跑，
  在跑就直接返回）—— 用户这时候要看识别画面做动作。
- **识别结束后再收回焦点**（`_finished` 里 `after(300, self._grab_focus)`）——
  这时用户要操作按钮了。

**教训**：「抢焦点」要看**用户此刻在干什么**。之前只顾着修「按钮点不动」，
没考虑识别期间用户根本不在看控制台。

### 二、⭐「全是错误」= 朝向反了（配置假设了机位方向）

`squat.json` 的 `knee_over_toe` 用 **`dxs`（带符号水平差）**，配置注释里写着
「人面朝画面右侧时写 `[脚尖, 膝]`」—— **朝向反了，符号整个反过来，
每一次都会报「膝超脚尖」**。而 CLAUDE.md 里早记着「用户尚未确认朝向」。

与其让用户去迁就机位，不如**让程序自己判断朝向**：

```python
@staticmethod
def estimate_face_sign(pts, vis=None, min_vis=0.5):
    """
    依据：脚尖总在脚踝的前方。取左右两脚 (脚尖x − 脚踝x) 之和，符号即朝向。
    返回 +1 面朝右 / -1 面朝左 / 0 判不出来（脚被遮挡时宁可返回 0 也不瞎猜）。
    """
```

配置里加开关 `"face_relative": true`，`dxs` 会先按朝向翻正再和阈值比。
**验证**：把合成骨架左右镜像后，标准深蹲和「膝前移」的评分**完全一致**
（78.3 / 33.2），说明同一份配置对左右朝向都成立。

> 这是一个值得记住的设计原则：**凡是依赖「左右方向」的信号，都必须先把方向归一化**，
> 否则配置就偷偷绑定了机位朝向 —— 而这在真实使用中根本不可控。

### 三、⭐「不计数」= 校准基线被采错，而画面上没有任何提示

站立基线自动校准的注释写着「启动头 2 秒你应该是站着的」。但如果用户那 2 秒
正在**调机位 / 走进画面 / 没站直**，基线就采错了 → 门槛 = 基线 − 15° 被设到
不可能达到的位置 → **表现为怎么做都不计数**。

**关键问题：这个提示只在终端打印，画面上完全看不到。**

**改法**：HUD 顶部加校准引导（黄底）——

```
请站直别动 · 正在校准基线 1.4 秒        ← 黄色，倒计时
请站到画面里 · 需要全身入镜才能校准      ← 没检出人时的提示
基线校准完成：站立 178°                 ← 绿色，只提示一次
```

### 四、「卡住」很可能是 MediaPipe 启动等待（61 秒）

`mediapipe 0.10.35` 启动时会尝试上传遥测，**网络超时导致卡约 61 秒**才出画面
（见「mediapipe 版本坑」）。这段时间画面全黑、日志只有一行 —— 极容易被当成卡死。

**改法**：UI 状态栏和运行日志都明确写出「首次初始化约需 1 分钟，**不是卡死**，请稍候」。

### 验证

- `test_pose_logic.py` 增至 **30 项**（新增朝向自适应测试：左右镜像后评分必须一致、
  错误动作在两种朝向下都必须被抓住）。
- 三个配置校验零错误；UI 启动确认无报错。
- ⚠ **真人摄像头的实际表现仍需用户复测** —— 上面三条是从代码和合成轨迹推出来的
  **最可能原因**，不是实测结论。若复测后仍有问题，需要终端日志才能继续定位。


## 2026-09-29 动作模块逐行审查（用户要求「仔细检查一遍」）

对 `pose_logic.py`（666 行）+ 三份配置做了系统审查：状态机、质量判定、信号计算、
主流程、配置数值、真机阈值合理性。**发现 6 个问题，其中 1 个是「全是错误」的真正元凶。**

### ⭐⭐ 一、极值约束在「没有数据」时用占位值误报（最严重）

```python
# 修改前
value = r_peak if r_peak is not None else 0.0      # peak_min：没数据 → 用 0
ok = value >= limit                                # 0 >= 160 → False → 报错！
value = r_valley if r_valley is not None else 999.0  # valley_max：没数据 → 用 999
ok = value <= limit                                # 999 <= 105 → False → 报错！
```

**`r_peak is None` 的真实含义是「本轮根本没采到极值」——通常因为关键点一直不可信**
（人站太远 / 身体没照全）。这时拿 0 或 999 去比，**「看不清」就被判成了「动作不到位」**：

```
模拟「本轮没采到极值」：
  not_deep_enough              value=999.0  ok=False  visible=True  ❌ 误报
  right_not_deep_enough        value=999.0  ok=False  visible=True  ❌ 误报
  not_standing_straight        value=0.0    ok=False  visible=True  ❌ 误报
  right_not_standing_straight  value=0.0    ok=False  visible=True  ❌ 误报
```

**这正好解释了用户反馈的「全是错误」** —— 只要身体没照全，**每一轮都报这四条**。

**改法**：`r_peak / r_valley` 为 None 时判为**「无数据」**（`visible=False`），
既不报错、也不参与评分。**「看不清」和「做不到位」必须区分开** ——
前者要提示用户调机位，后者才该纠正动作。

### 二、朝向判不出来时「静默退回用原始符号」

`face_relative` 的翻正逻辑原来写成 `if face_relative and self.face_sign:` ——
`face_sign == 0`（脚被遮挡、判不出朝向）时**不翻正就往下走**，等于赌用户面朝右边。

改成：**判不出朝向就直接让这一帧无效**（返回 None），交给可见性逻辑处理。

### 三、膝超脚尖的阈值 -0.10 偏严（蹲得标准反而被罚）

参数扫描暴露的现象：

```
深度  80° → 72.9 分     ← 蹲得比 90° 更深，分数反而更低？
深度  90° → 83.4 分
```

根因：**深蹲越深，膝越靠前**（几何必然）。而 `knee_over_toe` 的阈值 -0.10
在 80° 深度时就会被触发 —— **「蹲得标准」被罚分**。而运动科学界早有共识：
**深蹲到底时膝盖本来就会超过脚尖**。

改成 `min: -0.15` / `ideal: -0.06` 之后，深度扫描变成**漂亮的倒 U 形**：

| 深度 | 75° | 85° | **90°** | 95° | 110° | 130° |
|---|---|---|---|---|---|---|
| 分数 | 80.3 | 83.6 | **84.8** | 78.4 | 66.8 | 51.4 |

峰值正好落在大腿平行的 90° —— 这才是符合运动学的评分曲线。
膝前移也变得渐进：5° 不罚 / 10° 及格（62.5）/ 20° 以上重罚（约 35）。

### 四、`reset()` 有完全重复的代码

`sig_peak` / `depth_valley` / `rule_ext` / `last_values` 被清了两遍（合并遗留）。
功能无影响，但会让人误以为两部分有区别。已合并并补上说明。
另外明确注释：**`face_sign` 故意不在 reset 里清**（朝向是人的属性，清零计数不该忘掉它）。

### 五、HUD 把「无数据」显示成 `0.00`

`f"{(c['value'] or 0):.2f}"` 会把 `None` 显示成 `0.00` —— 看起来像「实测值就是 0」，
反而更难排查。新增 `_fmt_num()`：**`None` 显示成 `--`**。

### 六、`load_action` 缺容错（自定义动作场景）

原来直接 `Action(json.load(f))`，配置写错就抛 `KeyError: 'counter'` ——
对写配置的用户毫无帮助。现在给出具体说明：

```
动作配置 xxx.json 缺少 counter 段（计数配置）
动作配置 xxx.json 不是合法 JSON：第 1 行第 3 列 —— Expecting property name...
动作配置 xxx.json 的 counter 既没有 conditions，也没有 signal —— 至少要给一种计数方式
```

### 审查中确认**没有问题**的部分（也记录一下，避免重复怀疑）

- **计数状态机**：连续满足（`enter_hold`）+ 最短持续（`min_active_duration`）+
  最小间隔（`min_interval`）三层逻辑严谨；时间倒流不会误计数；`stage` 切换对称。
- **基础几何**：`angle_between` 在关键点重合时返回 `None`（而不是伪造 90°）。
- **配置正确性**：所有「右侧」约束**都写了 `signal` 字段**（我一开始漏看字段误判成 bug，
  用行为验证 —— 检查 `rule_ext` 里是否有该规则 —— 才确认是好的）。
- **显示层防护**：`realtime_pose.py` 的相关格式化早有 `is not None` 判断。

### 验证

  - 测试 31「没有数据 ≠ 动作不到位」：无数据时误报必须为 0、不得用占位值、不参与评分；
    有数据时必须照常判定。
  - 测试 32「朝向判不出时不做方向相关判定」。
- 三份配置校验零错误；参数扫描曲线符合运动学预期。


## 2026-09-29 修复「识别窗口按 q 退不出」

用户反馈：动作识别画面里按 `q` 没反应，退不出去。

### 根因：窗口焦点只抢了一次

macOS 上从命令行启动的 OpenCV 窗口**默认拿不到键盘焦点**，`q` / `r` 自然没反应。
原来的代码只处理了一次：

```python
            if not got_first:
                got_first = True
                cv2.waitKey(1)
                bring_window_to_front()      # ← 只抢这一次
```

**问题是这一次未必抢得到** —— 如果那一瞬间恰好被别的窗口抢回去
（比如测试控制台刚才也在抢焦点），**之后就再也没有机会了**，
用户看到的就是「按 q 完全没反应」。

### 改法（一）：让抢焦点真正生效

用户复测后**仍然按 q 没反应**，继续深挖发现原来的抢焦点代码**做的事情不够**：

```python
app.setActivationPolicy_(NSApplicationActivationPolicyRegular)
app.activateIgnoringOtherApps_(True)      # ← 只做了这两步
```

两个问题：
1. `activateIgnoringOtherApps_` 在 **macOS 14+ 已废弃**，macOS 26 上常常无效；
2. **「激活 App」≠「窗口拿到键盘焦点」** —— 缺了最关键的一步：
   把窗口设成 **key window**（`makeKeyAndOrderFront_`）。

现在做三层：

```python
app.activate()                              # macOS 14+ 的正规做法
NSRunningApplication.currentApplication().activateWithOptions_(…)   # 换个角度再激活一次
for w in app.windows(): w.makeKeyAndOrderFront_(None)   # ← 这一步才真正接管键盘
```

并加了**兜底诊断**：如果 `NSApp.windows()` 拿不到窗口，就用 Quartz 按 PID 查
系统级窗口列表，打印出来判断「窗口到底存不存在」，好决定下一步往哪修。

### 改法（二）：加一条**完全不依赖窗口焦点**的退出通道

与其一直跟 macOS 的焦点机制较劲，不如给一条一定有效的路：

> **在终端里输入 `q` 然后回车，就能退出。**

实现是后台线程读 `sys.stdin`，命中 `q` / `quit` / 回车就置位退出。

- **为什么可靠**：程序就是从终端启动的，**终端一定有键盘焦点**。
- **为什么不用全局键盘钩子**（pynput 之类）：那需要「输入监控」权限，
  又多一道系统授权；而 stdin 读命令**零权限**。
- **从 UI 子进程启动时** stdin 是管道，读不到东西会立刻结束 —— 已验证不影响主流程。
- 非 `darwin` 平台同样适用。

### 改法（三）：出画面后持续重试 + 醒目提示

1. **出画面后 8 秒内每 1.5 秒再试一次**（`focus_try_until` / `last_focus_try`），
   **一旦收到过任意按键就停止** —— 说明焦点已经在了，不该继续打扰。
2. **画面右上角常驻退出提示**：

   ```
   q / ESC = quit
   click the window if keys do nothing
   ```

   收到过按键后 15 秒自动撤掉（用户已经会用了，不必一直占地方）。
3. **UI 的运行日志**列出三种退出方式（按键 / 点关闭按钮 / 点「停止」），
   并说明「按 q 没反应就先点一下画面」。

另外 `r`（清零）现在也会在终端打印确认，用户能立刻知道按键生效了。

### 为什么不能靠「一直置顶」解决

置顶（`-topmost`）**不等于有键盘焦点**，而且会挡住别的窗口 ——
这正是之前「点击提示跑到 UI 后面」的元凶（见「UI 可用性修复」章节）。
**焦点和窗口层级是两件事，必须分别处理。**

### 验证

- 逻辑检查脚本确认四个关键点：8 秒内每 1.5 秒重试、收到按键即停、
  `stopped_reason="user"`、提示常驻直到收到按键。
- 40 项自动化测试全绿（本轮只改交互层）。
- ⚠ 实际按键手感仍需用户在系统「终端.app」里复测。


## 2026-09-29 对抗性边界测试（异常输入）

在逐行审查之后，又做了一轮**对抗性测试**：故意喂异常输入，看会不会崩或误判。
**发现 1 个真 bug、确认 4 类行为是稳健的。**

### ❌ 发现并修复：关键点数量不足会 IndexError 崩溃

```python
a.update([(100, 100)] * 5, ...)     # → IndexError: list index out of range
a.update(None, ...)                 # → 同样崩
```

正常情况 MediaPipe 总给 33 个点，但**异常时可能给不全**（模型内部出错、图像格式异常）。
后面按索引取点直接 `IndexError` —— 那会把整个识别主循环搞崩，**表现就是「画面卡住」**
（和之前 `f"{None:5.2f}"` 那次是同一类问题：**一帧异常数据毁掉整个循环**）。

**改法**：`update()` 开头就检查 `points is None or len(points) < 33` → 直接丢这一帧。

### ✅ 确认稳健的四类行为（写进测试，防止以后改坏）

| 场景 | 结果 |
|---|---|
| 点数不足 / 空列表 / None | 不崩、不计数 |
| NaN / 负坐标 / 超大坐标（10⁹） | 不计数 |
| 时间倒流 / 时间停滞 / 时间跳跃 | 不会凭空多计（`now` 变小时持续时间算成负数，自然不满足） |
| 关键点 ±5px、±15px 抖动 | 计数稳定（2 次就是 2 次，不因噪声乱计） |
| 只蹲下不起身 / 蹲到半路停住 | 不计数（`min_active_duration` 挡住「进了 active 但没做完」） |
| 完整往返后静置 5 秒 | 只计 1 次，不重复 |

**这轮测试也纠正了我自己两次错误的测试写法**（值得记下来）：
- 写「快速抖动」时用了「50% 概率在站立/蹲下之间随机跳」，结果计数 5 —— 但那是
  **数学上必然的**（随机序列里确实会出现「连续 8 帧 act + 连续 2 帧 rest」），
  真实抖动幅度小得多。改成 ±5~15px 噪声后计数稳定。
- 写「只做半个动作」时用了 `half * 3`，但**重复序列本身包含「从半蹲跳回站立」**，
  等于自己造出了往返。改成正真「蹲下后保持不动」才是对的。

> 教训：**测试写错比代码写错更隐蔽** —— 它会让你去修一个根本不存在的 bug。
> 看到「不符合预期」时，先怀疑测试，再怀疑代码。

### 验证

- `test_pose_logic.py` 增至 **33 项**，全绿（新增测试 33 覆盖上述全部场景）。
- 三份配置校验零错误。


## 2026-09-29 修复「膝超脚尖」误报（真机实测反馈）

用户实测反馈：**深蹲时高频率报「膝盖超过脚尖」，但实际上并没有超。**

### 根因：判据依赖了全身**最不可靠**的关键点

原来的判据是 `dxs`（脚尖x − 膝x，再除以小腿长）：

```json
{"signal": "dxs", "points": [31, 25], "unit_points": [25, 27], "min": -0.15}
```

**问题出在脚尖（landmark 31/32）上** —— 侧视机位下脚部最容易被遮挡、穿鞋时落点飘、
MediaPipe 对它的估计误差远大于膝/髋这些大关节。

实测这个误差有多大：

| 脚尖点偏移 | `dxs` 变化量 | 后果 |
|---|---|---|
| 0 px | — | 正常 |
| 10 px | +0.052 | 尚可 |
| 20 px | +0.105 | 接近阈值 |
| **30 px** | **+0.157** | **超过阈值 0.15 → 必然误报** |

**一次完全正常的关键点估计误差，就足以把「标准深蹲」判成「膝超脚尖」。**

### 改法：换成「小腿前倾角」（膝→踝），**完全不看脚尖**

```json
{"name": "knee_over_toe", "signal": "tilt", "points": [25, 27],
 "check": "peak_max", "max": 45, "ideal": 33, "priority": 70}
```

新判据只用**膝**和**踝**两个稳定点，而且 `atan2(dx, dy)` **自带归一化** ——
连「归一化基准」这个会抖的尺子都不需要了（这正是设计经验第 7 条
「能用角度就别用距离」的又一次应验）。

**实测值域**（合成轨迹）：

| 下蹲深度 | 75° | 85° | **90°** | 95° | 105° | 120° |
|---|---|---|---|---|---|---|
| 小腿前倾角 | 35.8° | 32.2° | **30.3°** | 28.6° | 25.3° | 19.8° |

膝前移越多，角度越大：前移 10°→38.8°，20°→48.9°，45°→74.3°。
所以 `max: 45`（正常范围 20~36°，留足余量）、`ideal: 33`。

### 效果对比

| 场景 | 旧判据 | **新判据** |
|---|---|---|
| 正常深蹲（深度 75~135° 全部） | 高频率误报 | ✅ **全部干净** |
| 膝前移 10~15°（轻微） | 误报 | ✅ 不报（合理） |
| 膝前移 20° 以上 | 报 | ✅ 报（并明显扣分） |
| **脚尖点偏 40px** | **必然误报** | ✅ **完全不受影响** |

### ⭐ 一条值得记住的判据选取原则

> **判据要用「最稳的关键点」，而不是「语义上最直观的关键点」。**

「膝盖是否超过脚尖」语义上当然要看脚尖 —— 但脚尖恰恰是姿态估计里最不稳的点
（遮挡、鞋子、朝向）。换成「小腿前倾角」后，**语义等价（膝前移 ⇔ 小腿前倾），
但只依赖两个稳定关节**，误报立刻消失。

选判据时按这个顺序问自己：
1. 这个信号**语义上**对得上吗？
2. 它依赖的关键点**在目标机位下可靠**吗？（侧视：脚尖/脚跟不可靠；正面：肩宽/脚距可用）
3. 它需要**额外归一化**吗？（要的话，那把「尺子」本身稳不稳？）
4. 有没有**角度版本**？（角度通常更稳，因为它自带归一化）

### 顺带调整

- **优先级 90 → 70**：它仍然是有意义的错误，但不该主导总分
  （原来一条就能把总分拉到 34 分，过于严厉）。
- **提示文案**也改成更可操作的：「小腿前倾太多，膝盖明显前移了 ——
  试着把髋部向后坐（像坐椅子那样）」。

### 测试调整

测试 29 / 30 里原来写的是**绝对分数线**（`assert knee < 45`），判据一改就失效。
改成**相对分差**（`assert std - knee > 20`）—— 要保证的是「明显变形必须显著拉低评分」，
而不是钉死某个具体分值。**断言要对「意图」敏感，而不是对「实现细节」敏感。**

### 验证

- 41 项测试全绿；合成轨迹 13 条用例全过；三份配置校验零错误。
- ⚠ 仍需用户真机复测确认误报是否消失。


## 2026-09-29 UI 美化（让它像个小程序）

用户要求「美化 UI，让它更像一个小程序」。

### 技术选型：**不引入新依赖**

考虑过 CustomTkinter / ttkbootstrap（真圆角、现代控件），但放弃：

- 它们的 API 与 tkinter **不兼容**，等于把 1000 多行界面**整个重写**；
- 而用户已经实机确认过当前 UI 可用 —— 重写会把「已经验证过的东西」重新变成未验证；
- 还要新增依赖，多一个环境风险。

改成**手工美化**：保持全部逻辑与控件结构不动，只换外观。

### 做了什么

**① 配色方案**（`BG/CARD/SOFT/BORDER/TEXT/MUTED/PRIMARY/...` 一组常量）

页面浅灰 + 卡片纯白，靠**底色差**区分区块 —— tkinter 画不出边框圆角，
硬加方框只会更土，不如用留白。

**② 卡片式布局**（`card()` 辅助函数）

每个功能区是一块白卡片，卡片之间留 12px 间距。

**③ 字体层级**（`F_TITLE/F_H2/F_BODY/F_SMALL/F_NUM`）

大标题 22pt / 卡片标题 14pt / 正文 12pt / 说明 11pt / **结果数字 26pt** ——
一眼能看出主次。

**④ 悬停反馈**（`hover_btn()`）

tkinter 默认按钮带立体边框（像 90 年代的对话框），全部压平成 `relief="flat"`，
再用 `<Enter>`/`<Leave>` 做变色反馈。**这是「像小程序」最明显的一步。**

**⑤ 控件换肤**（`setup_style()`）

`ttk` 在 macOS 上的默认主题是 `aqua`，**不允许改背景色**。切到 `clam` 之后
Entry / Spinbox / Combobox / Notebook / Progressbar 才能配合我们的配色。

**⑥ 按钮状态可视化**（`set_btn_enabled()`）

禁用时不只是 `state="disabled"`，还把底色切成灰 —— 一眼看出哪个按钮当前能点。

### ⚠ 踩的坑（两个，第二个比较危险）

**坑 1：tkinter 不允许同一容器混用 pack 和 grid**

第一版 `card()` 把标题 `pack` 在返回的容器上，调用方一 `grid` 就炸：

```
_tkinter.TclError: cannot use geometry manager grid inside ... which already
has slaves managed by pack
```

改法：标题放进**独立子容器**，返回一个**干净的内容区**给调用方自由使用。

**坑 2：整段替换 `_build` 时把后半部分删掉了**

用「找到 `def _build` 和下一个 `def` 之间的内容整体替换」的方式改写，
结果**连同后面两个标签页（历史与统计 / 运行日志）一起删了**。
语法检查通过（文件仍然合法），所以**不会报错**，只是功能静默消失。

幸好从 `git show HEAD:fitness_ui.py` 把原文捞了回来。

> **教训**：用「整段替换」改写大函数很危险 —— 语法检查只能保证文件合法，
> **不能保证功能完整**。安全做法是：改完后**清点关键控件是否都还在**
> （`grep self.report_list`、`grep self.log` 之类），或者干脆分小块替换。

- UI 启动确认无报错。

## 2026-09-29 完成「自定义健身姿势」模块（核心考点验收）

用户对照选题说明要求补齐这个模块：

> 用配置描述一个动作——参与判定的关键点、判定用的关节角度、上下阈值与迟滞区间、
> **计数方向与循环次数**。新增动作只需写一份配置，不必改代码。**这是本选题最有设计含量的部分。**

### 一、补齐「循环次数」（之前漏了这一项）

选题说明明确要求「计数方向**与循环次数**」，而「循环次数」我们一直没实现。

**含义**：**几个完整往返才算 1 次**。大多数动作是 1（蹲下再站起 = 1 次），
但有些动作天然成对 —— 例如「左右各划一次才算一组」「跳两下算一次」。

```json
{ "counter": { "cycles_per_rep": 2 } }
```

实现要点：在 `active → ready` 的退出点累加 `_cycles_done`，攒够才 `count += 1` 并归零。

⚠ **即使因 `min_interval` 被丢弃也要归零** —— 否则计数会被「扣住」，
用户得多做几轮才补上，手感很怪。

实测（同一段做 6 个往返的序列，只改配置）：

| `cycles_per_rep` | 1 | 2 | 3 | 6 |
|---|---|---|---|---|
| 计出次数 | 6 | 3 | 2 | 1 |

非法值（0 / 负数 / 小数）安全回退为 1，并会被 `validate_config.py` 拦下。

### 二、⭐ 修复一个浮点边界误判

做端到端验收时发现「3 次弯举只数出 2 次」。查下来是**浮点误差**：

```python
active_long_enough = self._rest_since - self._active_since >= self.min_active_duration
# 实际算出来：1.0 - 0.8 = 0.19999999999999996  <  0.2   → False
```

**「刚好达到 `min_active_duration`」的动作被误判成「太快了」而不计数。**

改法：时间差比较加 `- 1e-9` 容差。

> 教训：**凡是拿两个浮点数相减再比大小，都要留容差** ——
> 尤其是「刚好卡在边界」的参数，它在真实场景里也一定会发生。

## 2026-09-29 新增「自带数据回放测试」（用户澄清的真实需求）

用户澄清：**「我需要给一组数据，然后根据这个数据测试动作」** ——
不是让我再加一个动作，而是要一个**数据驱动的测试工具**。

### `pose_player.py`

```
读数据 → 逐帧喂给动作解释器（按 fps 推进时间轴）→ 出报告
```

**全程不需要摄像头**，也不需要重新做动作。

**数据格式**（最简形式，只给关心的关键点）：

```json
{
  "action": "squat",
  "fps": 30,
  "points": [23, 25, 27],
  "frames": [[[505,-151],[518,80],[516,300]], ...]
}
```

可选 `visibility`（给一个数或每帧一个数）—— **设 0 可以模拟「关键点被遮挡」**。

**输出**：计数 / 评分 / 错误事件汇总 / **每次计数的判定明细**（帧号 + 时间 + 分数 + 中文错误）。

### 设计上值得一提的三点

**① 报错必须是人话**

数据是用户自己提供的，**格式出错是常态**。所以 `load_data()` 做了充分校验，
报出「第几帧、第几个点、哪里不对」，而不是抛 `IndexError`：

```
第 0 帧有 1 个坐标，但 points 声明了 2 个关键点（[23, 25]）
points 里有非法编号 [99]（合法范围 0~32）
第 0 帧第 0 个坐标不是数字：[1, 'a']
```

**② 时间轴按 `fps` 推进**

动作里的 `enter_hold` / `min_interval` 都是**秒**。帧率给错的话防抖判定会整体偏掉 ——
所以 `fps` 是数据文件里的关键字段，不是可有可无的元信息。

**③ 缺的点判为「无数据」，而不是报错**

只给计数需要的 3 个点时，质量约束里用到其他点的那些会判为「无数据」
（这正是本轮修的那个 bug 的正面用法）—— **既不报错也不扣分**。

实测：同一段深蹲，只给 3 个点得 75.8 分，给全 33 个点得 78.2 分
（少判了几条姿态约束）。**想让某条约束生效，就得把它的 `points` 放进数据里。**

### 配套

- `motion_synth.py --export 文件.json`：把合成序列导出成数据文件，**当格式模板用**。
- `samples/` 放了三份示例：`squat_minimal.json`（7 KB，3 个点）、
  `squat_standard.json`（76 KB，33 个点）、`squat_shallow.json`（浅蹲，会报错）。
- 《自定义动作指南.md》新增第九节「用你自己的数据测试动作」。

  错误动作数据 / **6 类坏数据的报错**），合计 **44 项**，全绿。

### ⚠ 结论是「程序没问题」，但**我自己的测试写错了 5 次**

这一点比测试结果本身更值得记下来：

| # | 我写错的测试 | 错在哪 | 真相 |
|---|---|---|---|
| 1 | 「只蹲下不起身」 | 序列写成 `[站4帧]+[蹲30帧]` **重复 3 次** | 每次「蹲→站」本身就是完整往返，**计 2 次是对的** |
| 2 | 「站起到 148° 不该计数」 | 序列**重复 2 遍** | 第 2 遍开头那 5 帧 175° 正好补上了还原 |
| 3 | 「蹲到 142° 应该计数」 | **阈值语义搞反** | `lo=140` 是「信号 **低于** 140 才进入」，142° 大于它，**本来就不该计数** |
| 4 | 「蹲到 138° 不该计数」 | 同上 | 138 < 140 已进入动作，回到 175 就该计数 |
| 5 | 更早的「50% 随机抖动」 | 数学上必然产生往返 | 真实抖动幅度远小于此 |

> **教训（比任何一条设计经验都重要）**：
> **测试写错比代码写错更隐蔽** —— 它会让你去修一个根本不存在的 bug，
> 或者让你误以为功能坏了。
> 看到「不符合预期」时，**先怀疑测试，再怀疑代码**。
>
> 具体两个高频错误模式：
> 1. **重复序列偷偷造出往返** —— 想测「半程动作」时，只要序列里出现「蹲→站」的
>    衔接，就等于自己造了一次完整动作。测「不该计数」要用**单段、不重复**的序列。
> 2. **阈值语义记反** —— `lo=140` 是「低于 140 才进入」，不是「140 就是计数线」。
>    写断言前先在心里念一遍「谁大谁小」。

## 2026-10-12 「能否保证真人实测没问题」的诚实评估

用户问：不能配合测试，能否由我自行确认真人实测没问题。

**答：不能保证。** 以下是具体的证据与边界。

### 有证据的部分（可靠的）

用**真人级噪声模拟**（抖动 ±6px + 偶发跳变 1% + 局部遮挡 3% + 尺度漂移 ±8%
+ 机位游走 + 帧间隔不均匀）跑 8 组随机种子：

| 动作 | 计数稳定性 | 错误检测 | 评分范围 | 等级 |
|---|---|---|---|---|
| 深蹲·标准 | **8/8 都是 3 次** | — | 75~100 | 良好~优秀 |
| 深蹲·浅蹲 | **8/8 都是 3 次** | **8/8 抓到** | 43~57 | 待改进 |
| 俯卧撑·标准 | **8/8 都是 3 次** | — | 80~100 | 良好~优秀 |
| 俯卧撑·塌腰 | **8/8 都是 3 次** | **8/8 抓到** | 63~67 | 及格 |
| 开合跳·标准 | **8/8 都是 3 次** | — | 89~97 | 良好~优秀 |
| 开合跳·手不够高 | **8/8 都是 3 次** | **8/8 抓到** | 48~51 | 待改进 |

**阈值鲁棒性**：深蹲计数门槛 `lo` 在 120~170° 范围内（原值 140）都能正确计数，
还原线 `hi` 在 140~170°（原值 155）都能正确计数 —— **容差很宽**。

**结论：计数与判定的逻辑链路是可靠的。**

### 没有证据的部分（诚实的边界）

1. **阈值从未在真人视频上校准** —— 全是按运动学几何 + ACE/NASM 规范给的**工程初值**。
   真人的关节角度分布、体型差异、机位角度都会影响合适的阈值。
2. **真实 MediaPipe 的误差模式与我的模拟不同** —— 我的噪声是「高斯 + 偶发跳变」，
   真实情况可能有**系统性偏差**（比如某种姿势下膝盖点总是偏一点）。
3. **整条「摄像头 → 推理 → 判定」链路我一帧都没跑过**（本环境无摄像头权限）。

### 评分有波动，但这是正常的

即使是**完全干净**的合成数据，3 次深蹲的评分也在 **78~85** 之间（每次动作本身略有差异）。
加上噪声后扩展到 75~100，但**等级始终在「良好~优秀」**。

> **不要因为分数在 80 和 95 之间跳动就认为程序有问题** —— 这是正常波动。
> 真正异常的是「分数从 90 跌到 30」这种量级的变化。

### 一个失败的改进尝试（记录下来避免重犯）

针对评分波动，我试过加「离群帧过滤」（帧间变化 > 30° 就不采极值）。

**失败了**：它把**真实的大幅动作**也滤掉了 —— 测试 25（膝越过脚尖）用的手工序列
帧间变化 125°，被当成噪声滤掉，判定直接失效。已回滚。

> 教训：**「抗噪」不能靠「帧间变化阈值」** —— 真实动作本身就可能帧间剧变
> （快速起身、动作切换）。要抗噪得用**统计方法**（滑动窗口、分位数），而不是单帧判据。

### 真人实测时最可能出问题的三处（按风险排序）

| 风险 | 现象 | 应对 |
|---|---|---|
| **1. 摄像头拍不到人** | 检出率 0%，计数永远 0 | 已加明确提示。**这是最可能遇到的**，且不是程序问题 |
| **2. 阈值不合适** | 计数偏多/偏少、误报某个错误 | 所有阈值都在 `configs/*.json` 里，改数字即可，**不用改代码** |
| **3. 机位/朝向不对** | 角度算出来和预期差很多 | 侧视动作别用正面机位；界面里可切摄像头 |
